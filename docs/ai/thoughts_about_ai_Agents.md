# 对Agent的一些思考

印象中是从去年初开始小量的体验了AI编程，试用也局限在几个国产模型和github免费送的`copilot`，当时的感觉就是还是幻觉过多，注意力不够，做做小玩具都勉强，最多辅助代码提示和代码自动化模板。尤其对vibe这种行为是非常嗤之以鼻的，因为它基本只能制造垃圾。
时间一转来到2025年中，因为时不时还是会通过AI去做一些辅助的工具，渐渐就发现时代变了，各类模型的能力好像突然越过了某个临界点, 尤其各类code agent对AI coding的工程范式也在不断提升，我也逐渐从AI辅助和代码提示，小规模生成代码片段，逐步转到整个项目全部由AI生成，人在其中只负责规划方案，选型，验收。尤其是一些小型不上生产的项目，连代码review都省了。
我认为一方面是模型能力确实在飞速提升，但另一方面，Agent的工程化落地，更成熟的实践，约束，工程范式也是非常重要一环，重要性甚至超过模型提升的程度。

### 沟通形态

记得在今年也就是2026年年初还和朋友讨论以后的AI工程落地方式到底应该是怎么一种形态，朋友比较推荐的是`n8n`的模式，而这时候openclaw很火热，到处掀起养虾热，而我刚好也更看好类似chat这种模式。

先说说我理解的这两种模式差异在哪里

- `n8n`我理解中它确实是当前AI的能力能落地到生产级别项目的一个比较优秀的解法，人在中间扮演的角色是掌控整个业务流，首先他知道他要做什么，其次他规划好整个方案的走向，agent在其中作为牛马解决实际问题，而且这种方式只要保证每个节点的输入，还可以通过自动化验证输出。这是在做解答题。
- 而chat这种方式，或者通俗一点的叫傻瓜模式，通过自然语言描述需求，让agent自行做出设计和实施计划，自行做好处理业务流，划分节点，自己设计测试和验证。人在其中扮演的就是弱智甲方和脑瘫产品，只需要说“我要怎么怎么”，剩下的是做选择题。当然这种模式在现今还是有非常多问题，尤其是要落地到生产，实际是相当不可靠的。但这个模式我认为才是未来的发展方向，就目前市面上agent的实践方向上来看，也佐证了这个说法。


不过现在是2026年年中了，模型参数也不断加码，更多的训练参数是有极限的，虽然这个极限我不知道什么时候见顶，但很可能不会太远。模型厂商很可能会朝着微调和特化方向前进了，毕竟LLM的本质就是在巨型样本中找到最符合概率的答案，既然是概率学问题，那越往后参数量的大小边际递减的效应会越明显。那对我们而言，可以预见的未来模型不会有新的能力出现，最多就是更少幻觉，更长的上下文，注意力可以保持更久。不过即便是这样，现在的AI能力已经到了可以生产落地的拐点，已经不再是有点意思的玩具了。那么往后AI的能力能发挥到什么程度，全靠Agent的设计和工程实践。这个应该才是工程落地最关键的点。

话说回上面的模式差异，大模型的定位就应该是脑替，降低人各类工作的心智负担，那设计计划和规划实施自然也是它应该负责的部分，这是它当前最擅长的部分。它设计的只要不是太过分，我们只负责验收就可以了。

### 存在的问题

目前做的一些业务就是按这个方向实施的，最近在用的claude code和opencode，都比较典型。首先从模式上就支持plan这种机制，流程就变成 做计划 -- 调整计划 -- 实施计划，但是用起来就发现几个问题

- 受限于模型上下文尺寸，Agent要非常有效的把计划任务细化到每个规模可控的程度，通过不同的子Agent执行，还要不停的总结压缩上下文。这个就只能等以后模型能力提升，比如deepseek现在有了非常便宜的1M上下文，这是可优化的范畴。
- 现在模型规划的方案和做的选型都过于普通，设计也非常中庸。当然这可以理解，毕竟中庸的方案权重最大。这到也不是什么特别大的问题，说明以后即使是使用AI也需要非常强的行业经验和评估方案的能力，不同人让AI做同样的东西，效果可能天差地别。当然模型厂商也可能特化某个方向的模型能力，把这部分差距渐渐缩小。
- 面对超过一定规模的项目解决需求，需要更强有力的记忆和检索系统。

这些问题一半靠模型厂发力，另一部分就需要更新的工程范式，和新的工具出现。

### 不同语言平台的影响

使用不同语言平台会明显拉大生产的质量

- 带GC的语言>自己管理内存的语言
- 强类型语言>弱类型语言
- 流行度高的语言>流行度低的语言
- 编译期检查更多的语言更有优势
- 并发友好且无锁的设计更可靠
- 纯计算函数和状态分离对AI更友好

这些看起来其实和人写代码遇见的困难差不多，都是可以降低人的心智负担。但还是有些不一样的，比如不需要语言有什么优雅写法，更不在乎各类语法糖了。

这么类比下来，就不得不提到`Golang`，真的适合AI来写，以前自己写嫌弃语言太简陋，抽象能力太弱，一写写一坨。交给AI去做反而非常有优势。

### 题外话

以前一直觉得移动平台，像是手机、平板这些设备对程序员而言基本没法当作生产力设备。核心问题在于怎么都没法在上面舒适的写代码，做东西。程序语言就是一套形式化符号系统，想要代码写的舒适，一个带完整符号的键盘是需要的，其次要好用的IDE提供辅助，之前最多也就vscode能提供server模式略微弥补一定，但不解决根本问题。

之前曾经想过，如果抛弃掉现有的语言语法习惯，改用图形化符号表达，这样是否就是对移动端这种触摸型输入设备友好了，写逻辑就拖拉一下。但缺陷就更多了，一个丢失了作为文本的优势，文本是可以很方便进行处理的，像是我们已经习惯很久的一些基础设施都没法用，比如版本比对要重新设计，然后抽象的习惯也受到影响。

不过现在一切都迎刃而解了，现在直接讲中文，自然语言开发了，九宫格拼音键盘都够用。最近好多项目我都是边钓鱼，边在河边拿手机开发。甚至怕手机没电，最近又专门买个平板干这个事情，想想还是挺微妙的。

### 人工智障勘误

> 以下勘误由 GLM 5.1 提供

#### 明确错误

1. **"可以预见的未来模型不会有新的能力出现"**（第20行）——这过于绝对。模型能力提升不仅依赖参数量，还有架构创新（如 MoE、推理时计算 scaling、强化学习后训练等），这些都是质变而非仅量变。历史上多次出现"见顶论"被打破的情况。

2. **"LLM的本质就是在巨型样本中找到最符合概率的答案"**——这个定义过于狭隘。现代 LLM 的训练包含 RLHF/RLAIF、思维链推理训练、工具使用训练等，已远超简单的概率拟合，尤其推理模型（如 o1/o3、DeepSeek-R1）表现出的链式推理能力不能简单归约为"概率匹配"。

#### 不合理之处

1. **"参数边际递减效应会越明显"的推论**——即使边际递减成立，也不能推出"不会有新能力出现"。算法效率的提升（如更高效的注意力机制、更好的训练策略）可以在不增加参数的情况下解锁新能力。

2. **"人扮演弱智甲方和脑瘫产品"的表述**——这是对 chat 模式的贬低式类比。实际上 chat 模式中人仍然承担关键决策：需求澄清、方案评审、优先级判断，这与"弱智甲方"有本质区别。

3. **"连代码 review 都省了"**（第7行）——即使是小型非生产项目，完全不 review 也存在安全风险和依赖引入风险，这个表述过于轻率。

#### 有争议的观点

1. **"Agent工程化的重要性超过模型提升"**（第8行）——这是一个核心争议。工程化确实重要，但模型能力的跃迁（如从 GPT-3 到 GPT-4）带来的收益是量级性的，很难说工程化一定比模型提升更重要。两者是乘法关系，缺一不可。

2. **"chat 模式才是未来发展方向"**（第17行）——n8n 式工作流 vs chat 式交互的优劣尚无定论。生产环境中确定性往往比灵活性更重要，工作流模式的可控性和可审计性在许多领域（金融、医疗）是不可替代的。两者更可能长期共存而非替代。

3. **"Golang 最适合 AI 写"**（第47行）——这有争议。Go 的简单性确实对 AI 友好，但 Python（生态最丰富、训练数据最多）、TypeScript（强类型+灵活性）也有很强的竞争力。文章自己也承认"流行度高的语言>流行度低的"，而 Python 的流行度远超 Go。

4. **"纯计算函数和状态分离对 AI 更友好"**（第43行）——理论上合理，但现实中 AI 在处理 FP 范式（如 Haskell、纯函数式）时并不比 OOP 更好，因为训练数据中 OOP 代码远多于 FP 代码，这里存在理论与实际的矛盾。

5. **"边钓鱼边在河边拿手机开发"**（第55行）——自然语言编程在移动端可行，但对复杂项目的架构调整、跨文件重构等操作，移动端的效率仍远低于桌面端，这种体验描述可能过于乐观。
