# 自己写blog太麻烦，想想什么时候丢给AI写算了

最近只要 coding plan 还有余量，就还能维持天才程序员的体面，余额清零则智商归零，基本也算是实现了以前中文编程的夙愿。

最近在忙活的几个项目：

* [vistty](https://github.com/LaoQi/vistty)
* [pgit](https://github.com/LaoQi/pgit)
* [banyan](https://github.com/LaoQi/banyan)

所有项目均为纯 VIBE，不含任何人工古法手艺，有好有坏。

## vistty：陌生领域的边界试探

<B>之前我认为通过纯 VIBE 进行编程，项目的复杂度和技术难度不应超出开发者过多，否则必然会完全不可控，只会生产纯粹的垃圾。</B>vistty 就是拿来试探这个边界的：

> Vistty 是一个直接运行在 Linux DRM/KMS 子系统上的虚拟终端仿真器，无需 X11 或 Wayland 显示服务器，定位类似 kmscon。同时附带一个 Wayland 窗口后端，用于在桌面会话内开发与调试。

我从未实现过 terminal，协议和标准一无所知，也没时间和精力去啃。不过协议兼容这种体力劳动交给 LLM 问题不大，语料里大把成熟实现；真正的风险在于没做过这类应用，对架构和数据结构没概念，AI 随意发挥很容易产出极烂的实现和内存爆炸——初期几个版本确实大面积出现这类问题。何况我也从未处理过 DRM 或 Wayland 直接渲染的软件，仅仅从 wiki 上扫过几眼。

按过往经验，这个项目除了早夭别无可能，大概率 terminal 正常功能还没搞定，业务就已经膨胀得完全失控。好在结果不错，也让我确认了一件事：<B>领导真的可以不用完全懂技术，但需要有技术品味，知道哪些指标是好的，哪些指标是坏的，然后有足够的余裕（token）去试错就行。</B>

这个项目坚持了几个反常规的方案，古法实施基本不可能这么干。一是 pure go、禁止引入 cgo，唯一原因单纯是不想处理麻烦的环境，代价是最麻烦的 DRM gbm 支持只能走类 FFI 机制访问——顺便也白白浪费了大量 token 验证了闭源 NVIDIA 驱动完全驱不动。二是在无 Wayland/X11 时强行支持 GBM 模式做 GPU 渲染优化，明知收益相当低，但跑在 z8350 的小棒子上确实提升不少，不算白做。

结论：非自己熟悉领域的项目，采用合适的工程方式，还是有机会得到不错的结果。顺带一提，主力模型是 GLM 5.1，部分 GLM 5.2——对模型能力的需求真没那么高，够到基线水平后，更看重的是工程化。

## pgit 和 banyan：一个真好使，一个调子起高了

pgit 是个 Go 写的个人 git server，http api 和内嵌 ssh 都能用，目前日常在跑，我挑不出什么缺点。它恰好是个反例：需求小而具体，VIBE 出来直接就能用。

banyan 就难堪了，Rust 写的 LLM gateway/agent 工具，一开始就奔着平台级去：多 provider、计费统计、daemon、dashboard……调子起得太高，写到一半才发现需求本身就是伪命题，自己根本没用下去，烂尾了。AI 没问题，是我给它派了个不该存在的活。

回看这三个项目，规律很清楚：<B>VIBE 的成败不在模型能力，而在需求是不是真的。</B>需求真实且边界清晰（vistty、pgit），AI 就能交付；需求是自己脑补的宏大叙事（banyan），AI 只会帮你更快地生产垃圾。

## 所以，什么时候把 blog 丢给 AI 写？

回到标题。写 blog 麻烦的点从来不是打字，而是组织语言、取舍内容、琢磨开头收尾——典型的「想到了但不想干」的脏活。这种活儿还犹豫什么，现在就丢：这篇的后半段就是直接塞给 AI 写的，我只负责把前半段的事实和感受糊上去，剩下的分段、收敛口水话，AI 干得比我利索。
